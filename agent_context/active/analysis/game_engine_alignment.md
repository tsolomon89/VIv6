# Vision Alignment: The Game Engine & The Fact Store

**Verdict**: Perfect Structural Alignment. The "Homoiconic Fact Store" is the *only* architecture that can support your "Game Engine" vision naturally.

A traditional SQL database would struggle with "Time Travel" and "Dual Modes". The Event/Record model makes them native.

## 1. The Core Mechanic: Data = Game State

| User Vision | Canonical Architecture | Implementation |
| :--- | :--- | :--- |
| **"Spreadsheet Management Simulator"** | **Universal RecordStruct** | The DB is literally one giant spreadsheet (Log) of Facts. |

## 2. The Innovation: Dual Operating Modes

You asked for **Organic Mode** (Real Time) vs **Simulation Mode** (Game Clock).
In the Canonical Architecture, this is handled via **Tenancy**, not separate codebases.

### Implementation: The "Shadow Account"

Every Real Account has a generic "Shadow" or "Sim" Account.

| Mode | Real Account (`acc-victory-real`) | Sim Account (`acc-victory-sim`) |
| :--- | :--- | :--- |
| **Data Source** | Organic (API inputs, User clicks) | Synthetic (Generated by scripts) |
| **Time** | `Date.now()` (Immutable) | `GameClock` (Mutable, Future) |
| **Effect** | Real money, real emails | Mathematical projection |

**The Engine doesn't know the difference.**
It just queries `WHERE account_id = :current_context`.
- To "Simulate", you switch the UI context to the Sim Account.
- You run a script that inserts 10,000 `Activity` records into the Sim Account with future timestamps.
- You "Play" the game by querying the Sim Account at different cached timestamps.

## 3. Finite Actions & Probability

### "Finite Capacity for Action"
**Logic**: A "Turn" has a cost.
**Implementation**: This is a **Resource Constraint** defined in Tier 0/1.
- Define a `FieldDef`: `action_points` on the `Account` object.
- Every `Activity` record subtracts from this pool (computed projection).
- If `sum(actions) > limit`, the Engine rejects the write.

### "Probabilistic Outcomes"
**Logic**: Actions increase probability of conversion.
**Implementation**: **Weighted Edges**.
- Converting "Unattributed Info" to "Attributed Lead":
    - Create a `ProbabilityMap` record (standard `RecordStruct`).
    - It links `Persona` -> `Product` with a `weight` (0.0 - 1.0).
    - Simulation Script: `if (Main.random() < weight) { create_conversion_event() }`

## 4. The "Data Collapse" (Unattributed -> Attributed)

You describe information "collapsing" into engagement.
This is **Identity Resolution** in the Fact Store.

1.  **Stage 1 (Unattributed)**:
    - `Activity` recorded.
    - `actor_ref`: `null`
    - `context`: `{ cookie_id: "xyz" }`
    - *This is a "Ghost" in the machine.*

2.  **Stage 2 (The Collapse)**:
    - User fills a form. We get `email: jane@acme.com`.
    - **Resolution Event**: A new `Activity` links `cookie_id: "xyz"` to `contact_ref: "rec-jane"`.

3.  **Rewind**:
    - The Engine can now recompute the past.
    - "Who was that ghost?" -> It was Jane. The history "collapses" into attribution.
